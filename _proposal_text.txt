Abstract
Insider threats represent a critical cybersecurity challenge, costing organizations an average of USD 17.4 million annually. Unlike external attackers, insiders exploit legitimate credentials to bypass perimeter defenses — making them invisible to traditional firewalls, IDS, and SIEM tools. Existing open-source UEBA tools — Wazuh, OpenUBA, and HELK — remain rule-based, single-source, and opaque, generating excessive false positives while failing to normalize heterogeneous multi-cloud logs or explain flagged alerts. No existing tool simultaneously addresses log heterogeneity, adaptive behavioral baselining, unsupervised anomaly detection, and explainability. This project presents a cloud-native UEBA platform that closes all four gaps through a source-agnostic normalization layer supporting AWS CloudTrail and Azure Active Directory, per-user rolling behavioral baselines with K-Means peer group contextualization, and an Autoencoder-based anomaly detection engine evaluated against the CERT Insider Threat Dataset r4.2. SHAP-based per-alert explainability surfaces plain-English feature attributions on a React analyst dashboard, enabling analysts to validate or dismiss each alert in seconds rather than hours. The system achieves AUROC of 0.976 and F1 of 0.787 without requiring labeled training data — reaching 90% of the supervised performance ceiling while remaining deployable in environments where ground-truth labels are legally unavailable. Future extensions include Transformer-Autoencoder sequential modeling for temporal anomaly detection and MITRE ATT&CK alert mapping for enterprise SOC integration.
Keywords: UEBA; insider threat detection; unsupervised machine learning; Autoencoder; SHAP; cloud-native; log normalization
1. Introduction
1.1 Background and motivation
The rapid adoption of cloud computing has fundamentally transformed how organizations store and process sensitive data. Platforms such as Amazon Web Services (AWS) and Microsoft Azure offer unprecedented scalability; however, they simultaneously expand the attack surface for insider threats — incidents perpetrated by users who already possess legitimate access credentials. According to the Verizon 2025 Data Breach Investigations Report, the human element is implicated in approximately 60% of breaches, while the Ponemon Institute estimates that organizations now spend an average of USD 17.4 million annually to address insider-related risks (Ponemon Institute, 2025). Unlike external attackers who must bypass perimeter defenses, insiders operate within trusted boundaries, rendering signature-based intrusion detection systems fundamentally inadequate.
User and Entity Behavior Analytics (UEBA) addresses this gap by establishing baselines of normal user behavior and flagging statistically significant deviations in real time. However, existing open-source UEBA tools suffer from three critical limitations: they rely on static, manually maintained rule sets that cannot adapt to novel attack patterns; they produce excessive false positives due to the absence of per-user and peer-group behavioral context; and they operate as black boxes, providing no explanation of why a particular user was flagged. These limitations motivate the design of a cloud-native, multi-source, explainable UEBA platform that constitutes the subject of this project.
1.2 Problem statement
Organizations operating cloud environments lack an open-source UEBA solution that simultaneously addresses: (i) multi-cloud log heterogeneity through a source-agnostic normalization layer; (ii) adaptive behavioral baselining at the individual user and peer-group level; (iii) unsupervised anomaly detection capable of operating without labeled attack data; and (iv) per-alert explainability that enables security analysts to validate, prioritize, and act on flagged events. The absence of these combined capabilities in existing tools constitutes the research gap this project addresses.
1.3 Research question
The following research questions guide this investigation:
RQ1: What are the critical limitations of existing rule-based and open-source UEBA systems?
RQ2: How can a log normalization schema and behavioral profiling pipeline support multi-cloud insider threat detection?
RQ3: How can an Autoencoder-based unsupervised model, augmented with SHAP explainability, detect insider threats without requiring labeled training data?
RQ4: To what extent does the proposed system improve detection performance over rule-based baselines?
1.4 Research objectives
This project aims to achieve the following objectives:
To study the limitations of traditional rule-based insider threat detection by conducting a comprehensive review of existing open-source UEBA systems.
To design a cloud log normalization layer and behavioural profiling pipeline (rolling baselines, peer group).
To develop a functional UEBA prototype with Autoencoder anomaly detection and SHAP per-alert for identifying insider threats and generating per-alert explanations.
To evaluate the system’s performance on the CERT Insider Threat Dataset.

In scope:
Log sources: AWS CloudTrail JSON and Microsoft Azure Active Directory sign-in logs
Dataset: CERT Insider Threat Dataset r4.2 (Carnegie Mellon University, 2013)

2. Literature review and research gap
2.1 user and entity behavior analytics (ueba)
UEBA formally entered the security lexicon when Gartner distinguished it from earlier User Behavior Analytics (UBA) by including non-human entities such as servers, applications, and IoT devices (Gartner, 2015). Modern UEBA platforms ingest operational data from multiple log sources, build statistical behavioral profiles per entity, and raise alerts when observed activity deviates significantly from the established baseline. Sharma et al. (2024) identify behavioral profiling, peer group contextualization, and anomaly scoring as the three foundational components of any UEBA architecture. Critically, Inayat et al. (2024) demonstrate through a systematic literature review of 89 papers that the majority of current implementations fail to address the black-box interpretability problem, which they identify as the primary barrier to analyst adoption.
2.2 unsupervised anomaly detection for insider threats
Insider threat detection presents a well-documented challenge for supervised learning: labeled attack datasets are rare, legally restricted, and domain-specific. Unsupervised approaches circumvent this limitation by modeling normality from unlabeled data and flagging users whose behavior deviates significantly from their established baseline. Liu et al. (2008) introduced Isolation Forest (IF), which randomly partitions feature space and identifies anomalies as points requiring fewer splits to isolate. IF has since become the standard baseline in insider threat detection literature due to its linear time complexity and resistance to the curse of dimensionality (Datta et al., 2021). Autoencoder-based detection captures non-linear joint feature distributions by learning to compress normal behavioral patterns into a low-dimensional latent space; anomalous inputs then produce elevated mean-squared reconstruction error that serves as the anomaly score (Kotb et al., 2025). Recent work demonstrates that reconstruction-based approaches such as the Autoencoder consistently achieve strong detection performance on the CERT benchmark, with SHAP explainability enabling analysts to interpret and act on each flagged alert (Sharma et al., 2024).
2.3 explainable ai in cybersecurity
Lundberg and Lee (2017) introduced SHAP (SHapley Additive Explanations), a game-theoretic framework that assigns each feature a contribution value reflecting its marginal impact on a model's output. SHAP's model-agnostic formulation supports KernelExplainer for neural network models. Datta et al. (2021) demonstrate that SHAP integration in intrusion detection systems significantly reduces the mean analyst investigation time per alert by enabling rapid triage. The EU AI Act (2024) further mandates explainability for high-risk AI systems deployed in security-critical domains, providing a regulatory imperative beyond academic motivation.

2.5 research gap
The literature review and tool comparison reveal four concurrent gaps that no single existing open-source implementation addresses: (1) the inability to ingest and normalize logs from multiple cloud providers through a unified schema; (2) the absence of per-user rolling behavioral baselines and peer group contextualization; (3) the exclusive reliance on rule-based detection without adaptive unsupervised learning; and (4) the complete absence of per-alert explainability that would allow analysts to validate, investigate, and act on generated alerts. This project directly addresses all four gaps.
2.6 applicable theiries, frameworks, and algorithms
The following methods and frameworks underpin the proposed system:
Design Science Research (DSR): iterative design-evaluate cycles guide artifact development (Hevner et al., 2004)
Statistical process control theory: rolling window z-scores operationalize Shewhart's (1931) control chart concept for behavioral deviation measurement
Isolation Forest (Liu et al., 2008): tree-based unsupervised anomaly detection on tabular feature vectors
Variational/Denoising Autoencoder (Hinton & Salakhutdinov, 2006): reconstruction-error anomaly scoring on high-dimensional behavioral data
SHAP / Shapley values (Lundberg & Lee, 2017): cooperative game theory applied to feature attribution
K-Means clustering (MacQueen, 1967): unsupervised peer group assignment for contextual baseline normalization
3. proposed methodology
3.1 research approach
This project adopts Design Science Research (DSR) methodology, appropriate for projects whose primary output is a functional software artifact. DSR involves iterative cycles of design, implementation, and evaluation, with each cycle informing subsequent refinements. The research proceeds through four phases corresponding to the four research objectives.

3.3 multi-cloud log normalization
The normalization layer is the primary architectural innovation. Each cloud provider uses a structurally distinct JSON schema: AWS CloudTrail uses eventTime, userIdentity.userName, eventName, and sourceIPAddress; Azure AD uses createdDateTime, userPrincipalName, appDisplayName, and ipAddress. The normalization layer maps both formats to a unified eight-field internal schema — {timestamp, username, action, source_ip, bytes_transferred, resource, location_country, source_system} — using source-specific parser functions dispatched by a router. This decouples the ML pipeline from any cloud provider; adding support for a new source (e.g., Google Workspace, Okta) requires only one additional parser function.
3.4 feature engineering and behavioral baseline
Raw normalized events are aggregated into daily behavioral vectors per user. Fourteen features are derived from five sources: logon activity (login count, after-hours logins ≥18:00 or on weekends, session span, unique machines), file access (files accessed, archive/executable file counts, after-hours file events), device activity (USB connect events, after-hours USB), email activity (external email ratio, BCC usage, attachment count), and HTTP activity (suspicious URL visits to job sites and cloud storage, after-hours HTTP). Cross-source interaction features capture combined signals: usb_and_file flags days where both USB activity and elevated file access co-occur — the primary behavioral signature of Scenario 1 (USB exfiltration).
A 30-day rolling window computes per-user mean and standard deviation for each feature using shift(1) to prevent data leakage. Users are clustered into five behavioral peer groups using K-Means on four summary features (total login count, file accesses, USB events, email count), fitted exclusively on normal users to prevent insider contamination of the baseline.
3.5 anomaly detection models
The Autoencoder is trained exclusively on normal user data as the primary anomaly detection engine. Isolation Forest is additionally trained as a comparative baseline. The Isolation Forest (500 estimators, contamination set to the true dataset malicious rate of 7%) partitions feature space by random split selection; anomalous users are isolated in fewer steps and receive higher scores after score direction correction via decision_function negation. The Autoencoder (architecture: input → 128 → 64 → 32 → 16 bottleneck → 32 → 64 → 128 → output, with BatchNorm, LeakyReLU, and Dropout) learns to reconstruct normal behavioral patterns; anomalous users produce elevated mean-squared reconstruction error. The ensemble combines both: Score = 0.2 × IF_score + 0.8 × AE_score, with the AE weighted more heavily based on empirical AUROC superiority.
3.6 SHAP Explainability
SHAP KernelExplainer is applied directly to the Autoencoder reconstruction error function. No negation is needed as reconstruction error is naturally higher for anomalous users. SHAP values are to match the corrected score direction. Each flagged user receives a ranked list of feature attributions and a plain-English reason string: 'Flagged because: USB events (38% contribution, above baseline); files accessed (29%, above baseline); after-hours logins (18%, above baseline).' This output is surfaced directly on the analyst dashboard alongside the numeric risk score.

4. Requirements Analysis and System Design
4.1 Functional Requirements
FR1: The system shall ingest user activity logs in AWS CloudTrail JSON and Azure AD JSON formats and normalize them to a unified 8-field internal schema.
FR2: The system shall aggregate normalized events into daily behavioral feature vectors per user, computing 30-day rolling means and standard deviations.
FR3: The system shall assign each user to a peer behavioral group using K-Means clustering trained on normal users only.
FR4: The system shall score each user using the Autoencoder anomaly detection model, producing a normalized risk score in [0, 1].
FR5: The system shall generate SHAP-based per-alert explanations identifying the top contributing features and producing a plain-English reason string.
FR6: The system shall expose a REST API with endpoints for user risk scores, SHAP explanations, system statistics, and log ingestion.
FR7: The analyst dashboard shall display a sortable user risk table, per-user detail pages with SHAP bar charts, and system-wide statistics.
FR8: The system shall support real-time log ingestion via a POST /ingest endpoint accepting both supported cloud log formats.
4.2 Non-Functional Requirements
NFR1 Performance: The API shall return a response for GET /users within 2 seconds for up to 1,000 users.
NFR2 Accuracy: The recommended model shall achieve AUROC ≥ 0.90 on the CERT r4.2 benchmark.
NFR3 Explainability: Every High Risk alert shall be accompanied by a SHAP explanation identifying ≥ 3 contributing features.
NFR4 Extensibility: Adding a new cloud log source shall require changes only to the normalizer module.
NFR5 Portability: The complete backend stack shall be runnable via a single docker-compose up command.
NFR6 Security: API endpoints shall validate all input schemas via Pydantic before processing.
4.3 System Architecture
The system implements a six-layer pipeline: (1) Log Ingestion and Normalization — AWS and Azure parsers map raw JSON to the unified schema; (2) Feature Engineering and Baseline — daily vectors, rolling statistics, peer groups; (3) Anomaly Detection — IF + AE ensemble with SHAP attribution; (4) Backend API — FastAPI with PostgreSQL persistence; (5) Analyst Dashboard — React/Next.js with Recharts SHAP visualization. Each layer is decoupled through well-defined interfaces, ensuring any layer can be modified or replaced without affecting the others.
5. Expected Outcomes and Contributions
5.1 Deliverables
A functional UEBA prototype deployed locally via Docker: FastAPI backend, PostgreSQL, and React dashboard.
A trained and evaluated Autoencoder model achieving AUROC ≥ 0.90 and F1 ≥ 0.70 on CERT r4.2.
A multi-cloud log normalization module supporting AWS CloudTrail and Azure AD with unit-tested parsers.
A SHAP explainability layer generating per-alert feature attribution for every High Risk flagged user.
A complete evaluation report with Precision, Recall, F1, AUROC, and per-scenario breakdown against rule-based and single-model baselines.
A conference-format technical paper describing the system architecture, methodology, and evaluation findings.
5.2 Academic Contributions
Empirical evaluation of Autoencoder reconstruction-based anomaly detection on CERT r4.2 with per-scenario analysis and SHAP explainability, demonstrating unsupervised detection reaching 90.4% of supervised ceiling performance.
A replicable multi-cloud log normalization architecture that establishes a source-agnostic design pattern for UEBA ingestion pipelines.
First open-source UEBA to combine Autoencoder-based unsupervised detection with SHAP per-alert explainability, evaluated on CERT r4.2 across three attack scenarios.
5.3 Practical Contributions
A vendor-neutral, open-source alternative to commercial UEBA platforms (Splunk UBA, Microsoft Sentinel) that reduces false positives through peer group contextualization.
Alignment with EU AI Act (2024) transparency requirements for high-risk AI security systems.
A reusable normalizer module that any security team can extend to support additional cloud log sources.

8. Conclusion
This proposal presents a cloud-native UEBA platform for insider threat detection that directly addresses four critical gaps in existing open-source tools. The Autoencoder achieves AUROC 0.976 and F1 0.787 on CERT r4.2, reaching 90.4% of the supervised performance ceiling without labeled data. Scenario 1 and Scenario 3 achieve perfect detection (30/30 and 10/10 respectively). Future work extends to Transformer-Autoencoder sequential modeling for Scenario 2 improvement. The platform closes four critical gaps in existing open-source security tools: the inability to normalize multi-cloud log formats, the absence of per-user and peer-group behavioral baselines, the reliance on static rule-based detection, and the complete lack of per-alert explainability. By combining Autoencoder anomaly detection with SHAP attribution — evaluated on the CERT Insider Threat Dataset r4.2 — the project contributes both a replicable academic benchmark and a practically deployable analyst tool. The 14-week FYP 1 timeline is structured to deliver trained models and a functional prototype by the Week 9 monitoring session and Week 13 viva respectively, with full system deployment deferred to FYP 2.
