# GitHub collection: changed provider representations

## Operational verification — 30 October 2026

A real project-repository poll returned two previously stored native event IDs
with different payloads, causing strict ingestion conflicts. The original raw
payload is not retained in the event table, so the precise changed fields cannot
be established retrospectively.

The backend's immutable native-event rule remains unchanged. When the GitHub
collector receives the exact native-payload conflict response, it saves a
content-addressed provider snapshot under the ignored local connected directory's
`github-event-revisions` subdirectory. These snapshots are private evidence, not
new activity events, model inputs, alerts, or additional accounts.

Only GitHub polls explicitly configured with `--revision-dir` use this handling.
Other errors, oversized payloads, corrupt archives and failed archive writes
remain failures. AWS queue acknowledgement and Cloudflare handling are unchanged.
Repeated snapshots are idempotent. Counters distinguish changed representations
(`provider_revisions`) from newly written files (`revision_snapshots_created`).

Verification: 38 collector/pilot tests and 13 Cloudflare/GitHub dependency tests
passed. A real bounded poll returned 94 records: 90 outside the selected window,
2 existing duplicate receipts, 2 archived revisions, 0 inserted events and 0
retained failures. These counts describe this poll only.

The four affected jobs were paused during the change. Configuration backups were
saved, and only reviewed changes to `scripts/collect_live.py` and
`scripts/local_pilot.py` were repinned. Backend health and source identity passed
before collection resumed. Scope, dates, actor schedules and model results were
not changed.

## Follow-up: native repository activity is available

A read-only request using the restricted App installation token returned two
repository activity rows. Exactly one matched the commissioning commit SHA,
the verified native bot actor ID and activity type `push`. The original activity
and a diagnosis receipt are saved privately under the ignored App state folder
as `commissioning-native-activity.json` and `activity-preflight.json`.

This proves native activity visibility through a second endpoint. It does not
complete the Events API round trip or enable recurring workloads. No new action
or dashboard event was generated by this check.

The actual response with the pinned API version `2022-11-28` contains `id`,
`node_id`, `activity_type`, `actor`, `after`, `before`, `ref`, and `timestamp`.
It differs from the repository Events schema and from the example fields shown
in the current documentation. Implement against a tested, versioned contract.

Integration requirements before this can feed the dashboard:

- Preserve the original activity payload and endpoint/API-version provenance.
- Carry verified repository context from the request, since the row has no repo.
- Keep activity IDs separate from Events API IDs while retaining the same native
  actor identity; never manufacture a `PushEvent` from an activity row.
- Deduplicate overlapping push evidence if both endpoints are collected; two
  observations of one push must not inflate behavioural event counts.
- Verify retries, conflicts, timestamp/resource mapping and durable ingest before
  enabling any recurring bot action schedule.

Reference: [GitHub repository activities API](https://docs.github.com/en/rest/repos/repos#list-repository-activities).
